# 数治通一期产品设计：第一阶段 · 治理基础

> 产品名：**数治通——数据治理与智能问数一体化平台**
> 本文档覆盖：第一阶段「治理基础」。本期不涉及第二阶段（质量管控）、第三阶段（数据应用工作台 / askdata 智能问数集成）、第四阶段（价值度量）。

---

## 1. 定位与目标

### 1.1 定位

数治通是面向企事业单位的数据治理与智能问数一体化平台。第一阶段（治理基础）的定位是：**先把数据的"家底"盘清楚**——

- 数据从哪里来、归谁管、按什么标准生产；
- 业务对象长什么样、字段长什么样、谁来认责；
- 一切变更、发布都走审批、留痕、可追溯。

本期只做"基础盘点 + 流程固化"，不做数据质量规则引擎，不做可视化问数（那是第三期的事），**本期不动 askdata**。

### 1.2 目标（本期结束时应达成的状态）

1. 一个试点领域（核电"设备—维修工单—备件"链路）完成业务对象、数据目录、数据标准、认责矩阵、审批流的端到端成果发布；
2. 资产与责任可关联查询：任一数据资产能查到它的业务含义、归属对象、遵循标准、责任链、来源系统、质量问题、发布服务；
3. 全部治理活动（标准发布、目录发布、认责确认）有统一的审批入口与待办列表，所有操作进入审计日志；
4. 种子数据完整覆盖试点场景，可直接用来演示。

### 1.3 非目标（本期明确不做）

- 数据质量规则编排、质量问题自动派单（第二阶段）；
- SQL 生成、自然语言问数、数据应用工作台（第三阶段，集成对象为 askdata：GitHub `a2393439531/askdata`）；
- 数据资产价值评估、KPI 看板（第四阶段）；
- 多租户隔离、外部单点登录。

## 2. 本期五大范围模块

### 模块一：业务架构与业务对象管理

**功能点：**

1. 领域管理：业务领域的新增、编辑、停用（如"设备管理""维修管理""物资管理"）。
2. 能力 / 流程建模：领域 → 业务能力 → 业务流程 → 流程节点的层级梳理。
3. 业务对象卡：每个业务对象一张"身份证卡"，见 §3 信息结构。
4. 流程节点挂载数据说明：每个流程节点挂接四项——
   - 产生什么数据（本节点输出的数据项）
   - 使用什么数据（本节点输入的数据项）
   - 谁录入（岗位/角色）
   - 谁审核（岗位/角色）
   - 按什么规则校验（引用数据标准编号）
5. 对象关系图谱：对象之间的关联关系（组成、引用、派生），带关系有效时间。

**产出：**

- 试点领域业务架构图（领域—能力—流程—节点）
- 业务对象卡清单（设备、维修工单、备件物料、辅助给水泵……）
- 流程节点数据挂载说明表

### 模块二：数据资源目录

**功能点：**

1. 双视图管理：
   - 业务视图：按业务领域 / 业务对象浏览目录
   - 技术视图：按来源系统 / 数据库 / 表浏览目录
2. 目录字段（见 §4）。
3. 发布状态机（见 §5），状态区分"已登记"（草稿入库）与"已发布"（正式对外）。
4. 下架检查：目录下架前检查是否有下游依赖（引用该目录的服务、指标、问数模板），有依赖则阻止下架并给出依赖清单。
5. 持续更新：已发布目录支持版本更新，走变更审批。

**产出：**

- 试点链路数据资源目录（业务视图 + 技术视图）
- 目录发布状态机落地（登记→补业务含义与责任→技术核验→归口审核→发布→持续更新）
- 下架依赖检查报告

### 模块三：数据标准管理

**功能点：**

1. 标准类型：术语标准、字段标准、编码标准、分类标准、参考数据五类。
2. 标准信息结构（见 §6）。
3. 标准版本管理：新版发布后旧版进入"历史版本"，差异点可对比。
4. 落标情况查询：输入一个标准编号，可查——
   - 哪些系统已落标（按标准实施）
   - 哪些系统有差异（部分实施 / 映射有偏差）
   - 哪些系统未接入（未实施）
5. 试点示例：标准 `STD-EQP-SAFETY-001`「设备核安全分级」（核安全 1/2/3 级、非核安全级），含允许值、校验规则、变更要求。

**产出：**

- 五类数据标准库（术语 / 字段 / 编码 / 分类 / 参考数据）
- 「设备核安全分级」标准示例及版本记录
- 系统落标情况矩阵

### 模块四：数据认责与流程管理

**功能点：**

1. "字段—流程—责任"矩阵（见 §7）。
2. 任职管理：责任人任职有效期（起止日期）、代理机制（责任人离岗时指定代理人，代理期间责任自动转移并留痕）。
3. 多维配置：按单位 / 基地 / 领域配置不同的认责方案（如和平基地与另一个基地的责任人不同）。
4. 质量问题派发：质量问题按类型（完整性、准确性、一致性、及时性……）派发给对应责任人，进入待办。

**产出：**

- 备件物料等关键资产的字段认责矩阵
- 任职有效期与代理配置记录
- 质量问题派发规则与派发记录

### 模块五：审批流程

**功能点：**

1. 三种业务类型走审批（见 §8）：
   - 标准发布审批
   - 目录发布审批
   - 认责确认审批
2. 待办列表：当前登录用户可见"待我审批""我发起的""我已审批"三个页签。
3. 审批意见：同意 / 退回（必填退回原因）/ 撤回。
4. 审批流转记录：每一步谁、在什么时间、做了什么决定，全部进入审计日志。

**产出：**

- 三类审批流配置
- 审批记录与待办看板

## 3. 业务对象卡信息结构

| 序号 | 信息项 | 说明 | 示例（辅助给水泵） |
|---|---|---|---|
| 1 | 对象编号 | 全局唯一编码 | `OBJ-EQP-004` |
| 2 | 对象名称 | 中文名 | 辅助给水泵 |
| 3 | 对象定义 | 一句话定义 | 用于事故工况下向蒸汽发生器供水的转动设备 |
| 4 | 归属领域 | 业务领域 | 设备管理 |
| 5 | 归口部门 | 管理责任部门 | 设备部 |
| 6 | 唯一标识 | 业务主键规则 | 设备编码（厂站+系统+设备号） |
| 7 | 主要属性 | 关键属性清单 | 型号、额定流量、核安全分级、投运日期 |
| 8 | 对象关系 | 与其他对象的关系 + 有效时间 | 组成→逻辑设备（2020-01-01 起）；型号→型号设备；实例→物理设备 |
| 9 | 产生/变更/使用流程 | 产生、变更、使用该对象的流程环节 | 产生：设备投运流程；变更：设备变更管理流程；使用：维修工单流程 |
| 10 | 涉及系统 | 信息系统 | EAM 设备管理系统 |
| 11 | 涉及目录 | 数据资源目录条目 | `CAT-EQP-DEVICE` |
| 12 | 涉及标准 | 遵循的数据标准 | `STD-EQP-SAFETY-001` 设备核安全分级 |
| 13 | 涉及服务 | 对外发布的数据服务 | 设备台账查询服务 |

**设备三码关系（种子数据体现）：**

- 逻辑设备：设计/功能位视角的设备（如"辅助给水泵 A 列"）
- 型号设备：采购/型号视角的设备（如"某型号给水泵"）
- 物理设备：现场实体视角的设备（含序列号的单台设备）
- 三者之间为关联关系，每条关系带**有效时间**（生效日期—失效日期），支持设备异动（如换型、移位）后的历史追溯。

| 字段 | 必填 | 说明 |
|---|---|---|

| 服务方式 | 是 | API / 文件 / 库表直连 / 暂不提供 |

## 5. 目录发布状态机

```
                        ┌──────────────┐
                        │   已登记      │  草稿入库，仅登记人可见
                        │  (draft)     │
                        └──────┬───────┘
                               │ 提交补录
                               ▼
                        ┌──────────────┐
                        │ 业务补录中    │  补业务含义与责任
                        │(enriching)   │
                        └──────┬───────┘
                               │ 补录完成
                               ▼
                        ┌──────────────┐
                        │ 技术核验中    │  技术侧核验表结构、口径
                        │ (verifying)  │
                        └──────┬───────┘
                               │ 核验通过
                               ▼
                        ┌──────────────┐
                        │ 归口审核中    │  走"目录发布审批"
                        │ (reviewing)  │  退回→返回业务补录中
                        └──────┬───────┘
                               │ 审批通过
                               ▼
                        ┌──────────────┐
                        │   已发布      │  正式对外，可被查询/订阅
                        │ (published)  │  变更→走变更审批→更新版本
                        └──────┬───────┘
                               │ 下架申请（检查依赖）
                               ▼
                        ┌──────────────┐
                        │   已下架      │  有依赖则阻止下架
                        │(deprecated)  │
                        └──────────────┘
```

要点：

- **"已登记" ≠ "已发布"**：只有走完技术核验和归口审批的目录才是正式资产。
- 下架前必须做依赖检查：被服务、指标、问数模板引用的目录不允许直接下架。

## 6. 数据标准结构

| 信息项 | 说明 |
|---|---|
| 标准编号 | 全局唯一，如 `STD-EQP-SAFETY-001` |
| 标准名称 | 如"设备核安全分级" |
| 标准类型 | 术语 / 字段 / 编码 / 分类 / 参考数据 |
| 版本 | 语义化版本，如 `v1.0` |
| 业务定义 | 该标准的业务含义说明 |
| 允许值 | 枚举值或取值范围，如核安全 1 级 / 2 级 / 3 级 / 非核安全级 |
| 权威来源 | 该标准口径的权威出处 |
| 责任主体 | 标准归口部门与责任人 |
| 校验规则 | 可执行的校验表达式或描述，如"必填，取值必须在允许值范围内" |
| 变更要求 | 变更需走的流程与通知范围 |
| 落标情况 | 按系统统计：已落标 / 有差异 / 未接入 |

**标准示例（种子数据）：** `STD-EQP-SAFETY-001`「设备核安全分级」v1.0——业务定义为设备按核安全重要度划分的等级；允许值：核安全 1 级、核安全 2 级、核安全 3 级、非核安全级；校验规则：必填且必须在允许值内；变更要求：变更需经设备部与核安全部门会签。

## 7. 认责矩阵要素（"字段—流程—责任"）

| 要素 | 说明 |
|---|---|
| 数据字段 | 具体到字段，如备件物料.物料编码 |
| 业务归口部门 | 该字段业务上的归口管理部门 |
| 权威来源 | 权威来源系统 |
| 源头流程 | 产生该字段的业务流程与节点 |
| 录入岗 | 负责录入的岗位 |
| 审核岗 | 负责审核的岗位 |
| 数据管理责任人 | 业务侧对数据质量负责的人 |
| 技术维护责任人 | 技术侧对系统/接口负责的人 |
| 任职有效期 | 责任人任职起止日期 |
| 代理 | 离岗时代理人及代理期限 |
| 配置维度 | 按单位 / 基地 / 领域分别配置 |

质量问题派发：质量问题按类型（完整性、准确性、一致性、及时性、唯一性）派发到认责矩阵中对应的责任人，责任人处理后关闭，处理过程留痕。

## 8. 审批流（三种业务类型）

### 8.1 标准发布审批

```
发起人（标准编制人）
  → 归口部门审核（部门负责人：标准口径是否正确）
  → 数据管理部门复核（平台管理员：格式、版本、关联是否完整）
  → 发布（状态变为"已发布"，版本号生效）
```

退回：任一环节可退回，必填退回原因，退回给发起人修改。

### 8.2 目录发布审批

```
发起人（目录登记人）
  → 技术核验（技术维护责任人：表结构、口径、更新频率是否属实）
  → 归口审核（归口部门负责人：业务含义、责任划分是否准确）
  → 发布（状态变为"已发布"）
```

退回：技术核验退回→返回"业务补录中"；归口审核退回→返回"技术核验中"或"业务补录中"（审批人指定）。

### 8.3 认责确认审批

```
发起人（数据管理责任人/平台管理员）
  → 责任人确认（被指定的各责任人逐一确认"已知悉并接受"）
  → 归口部门负责人审批
  → 生效（认责矩阵状态变为"已生效"，进入任职有效期）
```

任一责任人拒绝确认则整体退回发起人调整。

### 8.4 通用规则

- 所有审批动作（提交、同意、退回、撤回）写入审计日志；
- 待办列表按"待我审批 / 我发起的 / 我已审批"分组；
- 超时未审批可配置提醒（本期为手动催办，二期再做自动提醒）。

## 11. 验收标准

试点领域（核电"设备—维修工单—备件"链路）完成以下成果发布，即视为一期验收通过：

1. **成果发布完整**：业务对象卡（设备/辅助给水泵/维修工单/备件物料）、数据资源目录（已发布状态）、数据标准（`STD-EQP-SAFETY-001` 等）、认责矩阵（备件物料字段认责）、三类审批各至少一条完整流转记录。
2. **资产与责任可关联查询**：从任一已发布目录条目，能查到业务对象、遵循标准、责任链、来源系统。
3. **对象卡全链路可视**：从"设备"对象卡出发，能看到——
   - 包含数据（关联的数据目录条目）
   - 遵循标准（关联的数据标准）
   - 字段责任（关联的认责矩阵条目）
   - 来源系统（技术视图来源）
   - 质量问题（关联的质量问题记录）
   - 发布服务（对外发布的数据服务）
   - 支撑指标（该对象支撑的业务指标，如设备完好率）
4. **三码关系可追溯**：逻辑设备 / 型号设备 / 物理设备的关系带有效时间，历史异动可查。
5. **审批与审计闭环**：全部发布动作有审批记录，全部关键操作有审计日志，演示账号按权限矩阵验证通过。
